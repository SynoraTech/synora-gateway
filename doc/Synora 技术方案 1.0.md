# Synora 项目技术方案（第一阶段 MVP）

> 文档版本：v1.0
> 适用阶段：第 1–12 个月（单人作战、最低成本启动）
> 关联文档：《Synora 项目策划书（含合规设计）v3.1》
> 编制视角：资深 AI 应用工程师

---

## 0. 编制原则与读者说明

本方案严格遵循策划书第十九章"核心执行原则"，即：**聚焦核心、稳定立身、合规为先、风控前置、单人系统化**。所有技术选型都同时回答三个问题：

1. **能不能撑起"稳定可靠"这个核心卖点？**——这是 Synora 区别于普通中转站的护城河。
2. **单人能不能跑得动？**——必须可自动化、可远程、可异步。
3. **能不能在 1 万元以内启动？**——前期不上云原生大场面，VPS + Docker 起步。

本方案**不涉及**业务运营、合规、财务等已在策划书中写明的内容，只回答"用什么技术、怎么搭、按什么顺序上线"。

## 1. 技术目标拆解

将策划书中的商业目标拆成 6 条可验收的技术指标：

| 编号 | 技术目标 | 第 12 个月验收口径 |
|---|---|---|
| T1 | 网关可用性 | 月度对外可用性 ≥ 99.9%，旗舰客户专属通道 ≥ 99.95% |
| T2 | 故障自动恢复 | 单上游通道异常时，请求自动切换至备用通道的中位耗时 < 500ms |
| T3 | 调用透明度 | 每一次调用可回溯：上游通道、耗时、Token、成本、状态 |
| T4 | 风控响应 | Key 泄漏从检测到自动冻结 ≤ 5 分钟；异常消费 ≤ 1 分钟告警 |
| T5 | 单人运维负载 | 系统自动处理 ≥ 80% 的故障，每周人工运维 ≤ 5 小时 |
| T6 | 合规可证 | 全量调用日志可保留 90 天；可一键导出某客户的调用记录与计费明细 |

这 6 条是后续所有技术决策的"北极星"。任何一个组件如果不能直接服务于这 6 条之一，第一阶段就不做。

### 2.2 为什么是单体而不是微服务

单人作战、第一阶段月调用量预估在百万级，单体 Go 程序 + 水平扩展两个节点已经绰绰有余。**任何引入服务网格、K8s、消息队列的诱惑都要被拒绝**——它们解决的是规模问题，而 Synora 第一阶段的问题是"活下来"和"卖出去"。

但单体≠不分层。代码内部按"协议适配层 / 路由决策层 / 上游调度层 / 数据访问层"严格分层，为第二阶段拆分预留接口边界。

### 2.3 为什么不直接二次开发 One API / New API

社区里 One API、New API、FastGPT 等开源项目都能"开箱即用地"实现统一接入。但 Synora 选择**借鉴其协议适配代码，自研网关核心**，原因如下：

1. **品牌定位冲突**：One API 衍生项目天然带有"中转站"标签，与 Synora "企业级、合规、稳定"的定位相悖。客户做尽调时一搜代码同源会扣分。
2. **核心差异点无法外挂**：策划书定义的核心差异点"多通道智能容灾"必须深度内嵌在调度层，社区项目的路由能力（简单优先级/轮询）远达不到 Synora 要求。
3. **风控与可观测要求过高**：单 Key 日消费上限、异常消费秒级冻结、完整审计日志，社区项目都不完善，与其大幅改造，不如重写。
4. **合规风险**：使用社区项目的 LICENSE、署名条款，会让 Synora 主体在大陆维权时陷入与原作者的法律纠葛——这违背"主体海外化"的合规基石。

**实操妥协**：第一阶段开发，可以**研读** One API 的 `relay` 目录获取各家上游协议的字段映射经验（这部分是体力活，没必要重造），但所有代码独立编写、独立仓库、独立 LICENSE。

## 3. 核心模块技术选型

### 3.1 网关主进程：Go + Gin

**选型理由**：

- Go 的并发模型与 HTTP 流式转发天然契合，单进程能稳定承载数千并发 SSE 长连接。
- 编译产物为单一静态二进制，部署、迁移、回滚都是秒级，对单人运维极友好。
- 社区里 One API、New API 全部用 Go，参考样本最多。
- 与策划书 3.3 节选型一致。

**核心依赖（控制在 10 个以内）**：

- `gin-gonic/gin`：HTTP 路由
- `jackc/pgx/v5`：PostgreSQL 驱动（比 `lib/pq` 性能高一个量级）
- `redis/go-redis/v9`：Redis 客户端
- `ClickHouse/clickhouse-go/v2`：日志写入
- `prometheus/client_golang`：指标暴露
- `golang-jwt/jwt`：API Token 签发
- `sashabaranov/go-openai`：仅用于 OpenAI 协议结构体定义（不直接用其请求函数，而是自己写转发）

**目录结构（严格分层）**：

```

├── cmd/
│   └── server/main.go             # 入口
├── internal/
│   ├── api/                       # HTTP 层（Gin handlers）
│   │   ├── v1_chat.go
│   │   ├── v1_models.go
│   │   └── middleware/            # 鉴权、限流、日志中间件
│   ├── adapter/                   # 协议适配层（关键）
│   │   ├── openai/                # OpenAI 协议入口与出口
│   │   ├── anthropic/             # Claude /v1/messages 入口与转换
│   │   └── gemini/                # Gemini 适配
│   ├── router/                    # 路由决策（容灾核心）
```

**关键原则**：`adapter` 层与 `upstream` 层之间只通过中性的 `UnifiedRequest` / `UnifiedResponse` 结构体通信。新增一家上游或新增一种入口协议，只在适配层增量改动，调度层零修改。

### 3.2 协议适配层（差异化关键之一）

**入口协议**第一阶段同时支持三种，覆盖 95% 客户场景：

| 入口协议 | 客户场景 | 优先级 |
|---|---|---|
| OpenAI `/v1/chat/completions` | 通用，所有 OpenAI SDK 用户、LangChain、Dify | P0 |
| Anthropic `/v1/messages` | Claude Code、Cursor、Cline 等 Anthropic 协议客户端 | P0 |
| Gemini `/v1beta/models/*:generateContent` | Google AI Studio SDK 用户 | P2（第 6 个月） |

**为什么 P0 必须包含 Anthropic 原生协议？**

这是 Synora 相对于普通中转站的一个被严重低估的卖点。策划书目标客户里"大陆出海 AI 工具公司——AI 编程助手"是最高优先级，而这批客户的研发团队大量使用 Claude Code、Cursor、Cline——它们都依赖 `ANTHROPIC_BASE_URL` 环境变量切换网关，发送的是 Anthropic native 协议而非 OpenAI 协议。如果只支持 OpenAI 入口，这批客户用起来要么改代码、要么走半残的兼容层、要么失去 prompt caching 和 extended thinking 完整输出能力。

**协议矩阵实现**：

```
       入口协议 \ 出口通道   OpenAI   Anthropic   Gemini   DeepSeek
       OpenAI 入口            透传     格式转换     格式转换  透传
       Anthropic 入口         格式转换  透传        格式转换  格式转换
       Gemini 入口            格式转换  格式转换     透传     格式转换
```

"透传"意味着只换 base_url 和 key，不动 body 结构；"格式转换"意味着在 adapter 层做字段映射。第一阶段优先把对角线（透传）做完美，再补其它格子。Anthropic 官方自身提供了 OpenAI 兼容层（`https://api.anthropic.com/v1/`），所以 OpenAI 入口→Anthropic 出口在初期可以直接用 Anthropic 官方兼容层快速跑通，等成熟后再切到自实现的转换以拿到 prompt caching 等完整特性。

**实现要点**：

- 流式（SSE）输出格式在 OpenAI 与 Anthropic 之间字段差异较大，转换器必须做到**逐 chunk 转换、不缓冲整体响应**，否则破坏流式体验，旗舰客户立刻流失。
- Tool calling 字段映射是协议转换里最容易出 bug 的点，单独写一组测试用例（覆盖单轮、多轮、并行 tool call、嵌套 JSON schema）。
- 凡是无法 1:1 映射的特性（OpenAI 的 `logit_bias`、Anthropic 的 `cache_control`），转换器要么忠实丢弃并记录 warning，要么在响应 header 中告知客户端，**绝对不能静默吞掉**——客户端调试时排查不到原因会失去信任。

### 3.3 多通道智能容灾（核心差异点）

策划书 3.1 节定义的"能力二"是 Synora 的核心护城河，技术上落地为下列设计。

#### 3.3.1 通道（Channel）抽象

一个**逻辑模型**（如 `claude-opus-4-7`）背后挂载多个**物理通道**（Channel），每个通道有独立属性：

| 字段 | 含义 |
|---|---|
| `id` | 通道唯一 ID |
| `provider` | 上游提供商（anthropic/azure_anthropic/aws_bedrock/...） |
| `endpoint` | 上游 endpoint URL |
| `credential_ref` | 加密存储的凭据引用（不直接存明文） |
| `region` | 上游 region（用于地理分散） |
| `weight` | 静态权重（管理员手配） |
| `priority` | 优先级层级（主/备/灾备） |
| `customer_tier_allowed` | 允许接入的客户层级（旗舰专属/全员共享） |
| `health_score` | 实时健康分（0-100，动态计算） |
| `state` | 状态机：active / degraded / circuit_open / disabled |

#### 3.3.2 健康分（HealthScore）算法

健康分是 Synora 容灾决策的核心数据，由四个维度滑动窗口计算（窗口长度 1 分钟）：

```
HealthScore = 100
            - 40 × (失败率，5xx/超时/network_error 占比)
            - 30 × (429 率，归一化到 [0,1])
            - 20 × (P95 延迟超阈值的程度)
            - 10 × (上次故障的衰减分，按指数恢复)
```

得分映射到状态：

- `HealthScore ≥ 80` → `active`
- `60 ≤ HealthScore < 80` → `degraded`（降低权重但继续使用）
- `HealthScore < 60` → `circuit_open`（熔断 30 秒后半开试探）

#### 3.3.3 路由决策流程

每个请求到达后，调度层执行如下流程：

```
1. 解析请求中的逻辑模型名
2. 查询该模型所有通道，按 (customer_tier_allowed 匹配 → priority → health_score) 排序
3. 取最高优先级、健康分≥80 的通道作为主选
4. 若主选失败（5xx/超时/429），且失败原因属于"通道级故障"：
   a. 立即切换至次优通道，重发请求
   b. 切换最多 2 次，避免雪崩
   c. 记录该次切换事件至 ClickHouse
5. 流式响应中途断流，做"流式重试"：
   - 已经吐出部分 token：返回当前已得内容 + 错误码 599（自定义），不切换通道，由客户端决策
   - 还未吐出第一个 token：切换通道重发
6. 全部通道都失败：返回 503，触发 P1 告警
```

**关键细节**：

- **失败分类**：必须区分"通道级故障"（应切换）和"用户级故障"（应直接返回）。Token 超限、内容审核拒绝、参数错误属于用户级，原样返回；网络超时、5xx、429、socket reset 属于通道级，切换。
- **流式响应切换**：业界普遍做不好的点。Synora 的处理是"零字节切换"——只在首个 chunk 之前允许切换，已吐字节后切换会让客户端拿到拼接错乱的回复，反而比一次失败更糟。
- **请求级幂等**：客户端每次请求生成 `x-synora-request-id`，重试和切换共用同一 ID，方便客户排查。

#### 3.3.4 旗舰客户通道隔离

策划书 4.2 节承诺旗舰客户"专属通道隔离"，技术实现：

- 旗舰客户在数据库标记 `tier=flagship` 与 `dedicated_channel_group_id`
- 通道表的 `customer_tier_allowed` 字段限定通道仅服务于某客户组
- 路由层在排序前先按通道组过滤，未匹配通道不参与候选
- 旗舰通道完全独立的上游账号 + 独立 IP 出口，与共享池在物理层面隔离

这一隔离能力**是 Synora 收 8000-10000 元月费的硬支撑**，从第 5 个月签下首个旗舰客户时就必须完整可用。

### 3.4 数据存储

| 存储 | 用途 | 选型理由 |
|---|---|---|
| **PostgreSQL** | 主数据：用户/Token/通道/钱包/订单 | 关系型、事务、JSONB、单机扛得住 100 万用户 |
| **Redis** | 限流计数器、健康分缓存、Token 黑名单、会话 | 微秒级响应，必须 |
| **ClickHouse** | 调用日志：每次请求一行 | 单机日写入 1 亿行毫无压力，复杂分析秒级响应 |

**为什么调用日志用 ClickHouse 而不是 PostgreSQL？**

- 日均调用量预估第 6 个月达到 50 万次/天，第 12 个月 200 万次/天。PostgreSQL 在这个量级上做分析查询会拖慢主库。
- ClickHouse 单机能扛日均千万级写入，且压缩比 10:1 以上，存 3 个月只占数十 GB。
- 策划书 T6 要求"导出某客户 90 天调用记录"，ClickHouse 几秒就能跑完，PostgreSQL 要分区+索引大费周章。
- 自建 ClickHouse 月成本：复用同一台 4C8G VPS（用一块独立磁盘）即可，0 增量成本。

**调用日志表结构（ClickHouse）**：

```sql
CREATE TABLE call_logs (
    request_id      String,
    user_id         UInt64,
    api_key_id      UInt64,
    customer_tier   LowCardinality(String),  -- self/standard/flagship
    model_logical   LowCardinality(String),  -- 客户请求的模型名
    channel_id      UInt32,
    provider        LowCardinality(String),
    region          LowCardinality(String),
    ts_start        DateTime64(3),
    ts_first_token  DateTime64(3),
    ts_end          DateTime64(3),
    status_code     UInt16,
    is_failover     UInt8,
    failover_chain  Array(UInt32),  -- 切换链路
    input_tokens    UInt32,
    output_tokens   UInt32,
    cost_usd        Decimal(10,6),
    revenue_cny     Decimal(10,4),
    margin_cny      Decimal(10,4),
    error_type      LowCardinality(String),
    error_message   String,
    moderation_hit  UInt8,
    client_ip       IPv6,           -- 客户调用方 IP（合规用）
    user_agent      String,
) ENGINE = MergeTree
PARTITION BY toYYYYMM(ts_start)
ORDER BY (user_id, ts_start, request_id)
TTL ts_start + INTERVAL 90 DAY;
```

90 天 TTL 是策划书 8.3 节硬性要求，TTL 在表上设置，到期自动清理，零运维。

**凭据存储**：

PostgreSQL 表 `channels` 中只存 `credential_ref`，明文凭据存在加密文件 `/etc/synora/credentials.enc` 中，主密钥通过 systemd EnvironmentFile 注入，仅运行用户可读。第一阶段不引入 Vault 等专业 KMS，由 AES-256-GCM 加密 + 文件系统权限保护即可。

### 3.5 计费与钱包

**核心原则**：**预付费、实时扣费、绝对一致**。

- 计费维度：按 `provider × model × (input_tokens, output_tokens)` 三元组定价，配置在 `pricing` 表中，支持 cached_tokens 等附加维度
- 扣费时机：流式响应结束、统计完最终 token 数后，**异步**扣费（先记 ClickHouse 流水，再批量更新 PostgreSQL 钱包余额）
- 一致性保证：余额表用悲观锁更新，扣费前检查可用余额，余额负值时下次请求被拒
- 实时性 vs 性能：余额检查走 Redis 缓存（5 秒过期），扣费走 PostgreSQL 事务，两者最终一致

**充值通道（与策划书 6.5 节支付通道设计一致）**：

| 通道 | 集成方式 | 上线优先级 |
|---|---|---|
| Stripe（信用卡） | 官方 SDK | P0，第 1 个月 |
| USDT（TRC20） | 自建监听器（监听链上 transfer 到指定地址） | P1，第 3 个月 |
| 港币/美元对公转账 | 人工到账后管理后台手动充值 | P0（手动操作） |
| 支付宝/微信 | 第三方代理（如 PingPong），低调上架 | P2，第 6 个月后视情况 |

支付宝/微信不主动营销，落地页不提，由客户在"其它充值方式"折叠菜单中主动发现。

### 3.6 风控引擎

风控按策划书第八章五道防线落地，技术实现按"声明式规则"组织：

```yaml
# /etc/synora/risk_rules.yaml
rules:
  - id: api_key_daily_limit
    scope: api_key
    metric: daily_spend_cny
    threshold: 100        # 自助层默认 100 元/日
    action: pause_key
    notify: email

  - id: anomaly_burst
    scope: api_key
    metric: spend_per_minute
    threshold: 20         # 单分钟消费超 20 元
    action: rate_limit_50pct
    notify: telegram

  - id: moderation_hit_repeat
    scope: user
    metric: moderation_hits_in_24h
    threshold: 3
    action: rate_limit_30pct
    notify: email

  - id: github_key_leak
    scope: api_key
    trigger: github_secret_scanning_match
    action: revoke_key_immediately
    notify: telegram+email
```

规则引擎独立于网关主流程异步运行，每 30 秒扫描指标一次。这种声明式设计的好处是**改阈值不用改代码**——单人作战时，"凌晨发现 99 元日上限太低"的情况，改 YAML 重启即可。

**内容审核（策划书防线三）**：

- **入口侧**：本地维护一份关键词黑名单（涉政、涉黄、暴恐基础词库 2000 词），用 Aho-Corasick 算法做 O(n) 匹配，命中即拒绝并记审计日志
- **出口侧**：充分信任上游模型自带的 moderation（OpenAI Moderation API 免费，Anthropic 自带，DeepSeek/通义自带）
- 关键词库每月由运营人员（即创始人本人）人工 review 一次，不接入第三方实时审核服务（成本高且增加合规复杂度）

**GitHub Key 泄漏扫描**：

- 注册 GitHub Secret Scanning Partner Program（免费），按其协议接收 Webhook
- Synora API Key 设计带固定前缀 `sk-synora-` 便于 GitHub 识别
- 一旦收到泄漏通知，立即在 Redis 标记 Key 状态为 `revoked`，5 秒内全网生效
- 同时给用户发邮件通知并自动生成新 Key

### 3.7 可观测性（差异化关键之二）

**这一节是 Synora 区别于"中转站"的另一个硬核差异点。** 策划书反复强调"将稳定性做成可量化、可公开、可传播的资产"，技术上必须给得起这个承诺。

#### 3.7.1 三层观测

| 层级 | 工具 | 谁看 |
|---|---|---|
| 内部运维 | Prometheus + Grafana + Loki | 创始人本人，凌晨告警排查 |
| 客户控制台 | Synora 管理后台 | 企业客户查自家用量与故障 |
| 对外状态页 | 静态站 + 数据从 ClickHouse 拉取 | 全网公开，潜在客户、媒体 |

#### 3.7.2 对外状态页（差异化武器）

**这是 Synora 最重要的一个"反差武器"**——市面上的中转站几乎没有一家敢做透明状态页，因为他们的稳定性根本经不起公开。

状态页公开以下指标，更新周期 1 分钟：

- 各主要模型当前是否可用（绿/黄/红三态）
- 过去 24h / 7d / 30d 各模型的可用率与 P95 延迟
- 历史事件列表（每次重大故障公开复盘）
- 实时统计：过去 5 分钟成功请求数、当前活跃通道数

**实现极简**：

- 状态页前端：纯静态 HTML + 一个 JS 定时拉接口（不上 React，省维护成本）
- 后端只暴露一个 `GET /public/status` 接口，从 ClickHouse 物化视图读取预聚合数据，QPS 限制 60/分钟
- 部署：Cloudflare Pages 免费托管，0 成本
- 域名：`status.synora.xxx`，与主站同主域

#### 3.7.3 稳定性月报

每月 1 日由定时任务自动生成上月 PDF 报告，发送给所有企业客户邮箱，内容包括：

- 整体可用率、各模型可用率
- P50/P95/P99 延迟分布
- 故障事件清单（脱敏）
- 客户专属用量摘要（按客户定制）

这个月报既是合规材料也是营销武器，**它的存在本身就是给客户的安全感**。

### 3.8 管理后台

**第一阶段只做最小可用**：

- 客户面（嵌在主站登录后）：用量统计、Key 管理、充值、调用日志查询、月报下载
- 管理面（仅创始人）：客户管理、通道管理、定价配置、风控规则编辑、对账

技术栈：React + Vite + Ant Design Pro 模板。**不上 Next.js 之类的全栈框架**，前后端分离、纯静态部署到 Cloudflare Pages，调后端 API。

**重要克制**：第一阶段管理面允许有些操作走 SQL 命令行而不是 Web UI（如新增通道、调整定价），这能省下 1-2 周开发时间，且操作频次本来就低。

## 4. 部署架构

### 4.1 第一阶段（第 1-6 个月）：单可用区双节点

```
香港 VPS A (4C8G)         香港 VPS B (4C8G)
├─ Synora Gateway          ├─ Synora Gateway
├─ PostgreSQL (主)         ├─ PostgreSQL (流复制备)
├─ Redis (主)              ├─ Redis (sentinel/备)
├─ ClickHouse              ├─ (空闲热备)
└─ Caddy 反代              └─ Caddy 反代
        ↑                          ↑
        └──────── Cloudflare ───────┘
                  (DNS 负载均衡)
```

- 两台 VPS 部署在**不同机房**（同一供应商也可，至少不同物理位置）
- Cloudflare 做 DNS 层加权轮询 + 健康探测，单机异常自动剔除
- 数据库与 Redis 都做主备复制，故障切换走手动（凌晨被告警叫醒后 15 分钟内完成）
- 月成本：400-600 元（与策划书 3.3 节预算一致）

### 4.2 第二阶段（第 7-12 个月）：跨区域三节点

第二阶段当月利润突破 1 万元时升级：

```
香港 VPS A         台北 VPS B         新加坡 VPS C
├─ Gateway        ├─ Gateway         ├─ Gateway
├─ Postgres (主)  ├─ Postgres (备)    ├─ ClickHouse (远程备)
├─ Redis (主)     └─ Redis (备)
└─ ClickHouse
        ↑                ↑                  ↑
        └────── Cloudflare（地理路由）────────┘
```

- 客户请求按地理就近路由
- 应对"VPS 厂商跑路"风险（策划书 10.2 节）
- 月成本：1000-1500 元

### 4.3 部署方式

- 一切以 **docker-compose** 起步，单文件描述所有服务
- 部署脚本走 GitHub Actions：push 到 main 触发构建 → SSH 到目标机器 → `docker compose pull && up -d`
- **不上 Kubernetes**——单人维护 K8s 的运维负担远超它带来的收益
- 数据库迁移工具：`golang-migrate`，迁移脚本随代码版本进仓库

### 4.4 备份策略（对应策划书 10.2 灾备）

| 数据 | 备份方式 | 频率 | 异地存储 |
|---|---|---|---|
| PostgreSQL | `pg_dump` + WAL 归档 | 全量日 / WAL 实时 | Cloudflare R2（每日同步） |
| ClickHouse | `clickhouse-backup` 工具 | 每日 | Cloudflare R2 |
| 凭据文件 | 加密后 rsync | 每次变更触发 | 1Password 文档型条目 |
| 代码 | GitHub 私有仓库 | 实时 | 本地 Git mirror + 加密云盘 |

Cloudflare R2 的 10GB 免费额度足够第一阶段所有备份，0 成本。

### 4.5 网络与出口 IP

策划书 6.4 节要求"出口 IP 全球分散，不集中亚太"——这是规避 OpenAI/Anthropic 反作弊系统识别 Synora 为"大陆专用转售"的关键。

技术实现：

- 上游调用走 **HTTP 出口代理池**（不是 VPN），代理节点散布于美西、美东、欧洲、日本、新加坡
- 出口节点从 5-10 家小型 IDC 采购独享 IPv4，每个节点月成本 30-80 元
- 每个上游账号绑定固定 1-2 个出口节点，**长期稳定**而非每次随机切换（频繁切 IP 反而会触发供应商风控）
- 通道表中记录 `egress_node_id`，调用时按通道走对应代理

总出口预算：第一阶段 5 个节点约 250-400 元/月。

## 7. 单人产能保障的技术对策

策划书第十三章测算单人服务时长约 25-27 小时/月，要确保不被技术债务拖死，从一开始就要做好这几件事：

### 7.1 凡是会做两次的事，立刻自动化

- 客户注册、Key 创建、首次充值：完全自助，零人工介入
- 月度对账：定时任务自动跑、自动出报表、自动发邮件
- 新通道接入：写好 YAML + 一条命令导入，不要每次都打开数据库改表
- 退款处理：管理后台一键退款，自动回填钱包流水

### 7.2 告警分级 + 自动止损

策划书 10.1 节定义的 P0/P1/P2 告警，技术实现：

- **P0**（短信+电话）：全站不可用、数据库主备双挂、上游账号集体被封
- **P1**（Telegram）：单通道熔断、健康分骤降、风控规则触发
- **P2**（邮件）：客户余额低、调用量异常波动、月报生成完成

**关键设计**：告警必须**附带建议动作**，不能只说"有问题"。例如"通道 ch_03 熔断，请在管理后台点击 [一键切换备用]"。这能把凌晨告警的处理时间从 30 分钟压到 3 分钟。

### 7.3 灰度发布与可回滚

- 每次发版先发到 VPS B（流量较小），观察 1 小时无异常再发 VPS A
- 数据库 migration **永远只增不删**：加字段、加索引允许，删字段、改类型需要走多步骤迁移
- 每个版本打 Git tag，回滚就是 `docker compose pull synora:v1.2.3 && up -d`，1 分钟内完成

### 7.4 文档即代码

- 所有 SOP 用 Markdown 写在仓库 `docs/sop/` 下，跟代码一起 review
- 客户接入手册、API 文档用 mdBook 或 VuePress 生成静态站，CI 自动发布
- 故障复盘按模板写：时间线 → 影响 → 根因 → 改进项 → owner

## 10. 第二阶段技术规划（前瞻）

第二阶段（第 13-24 个月）月利润目标 5 万元，对应 8 旗舰 + 10 标准 + 80 自助。为该规模做准备的技术演进方向：

- **网关水平扩展**：从 2-3 节点扩到 5-8 节点，引入 Consul 或 etcd 做服务发现
- **数据库读写分离**：PostgreSQL 引入读副本，钱包扣费走主，查询走从
- **代码拆分**：网关、风控引擎、计费、管理后台拆为独立服务（不是微服务化，而是清晰的进程边界）
- **接入企业级合规凭证**：Azure OpenAI 企业版、AWS Bedrock 跨账号联邦
- **审计日志合规化**：增加防篡改链路（hash chain）以满足旗舰客户审计要求
- **首位招聘**：兼职运维上线后，把 P1/P2 告警的初步排查交给对方
- **SDK 与文档站建设**：前期允许客户用 OpenAI SDK，第二阶段提供官方 Synora SDK 与详细文档

第二阶段是否进 K8s 视团队规模决定——如果团队仍在 1-2 人，docker-compose 继续够用；如果扩到 3 人以上，再考虑迁移。
